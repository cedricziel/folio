# Design

## Context

See proposal.md (Why) for motivation. Current state, as found in the code:

- **Continuation today**: only `InboxView` handles a continuation (`.onContinueUserActivity(CSSearchableItemActionType)`). It parses `DocumentLink(spotlightIdentifier:)` (vault + document UUID, no server) and calls `handle(.document(id, vaultID:))` → `WorkspaceViewModel.open(_:vaultID:)`. `RootView` renders `AppLockView` _instead of_ `WorkspaceView` while `AppLock.isLocked`, so no continuation handler exists while locked: a Spotlight tap into a locked app is dropped today.
- **Navigation**: `WorkspaceViewModel.open` already selects the vault, reports `"This vault is no longer available."` for unknown vaults, and pushes the document onto the All-documents path. `InboxView.documentDestination` already shows "Document unavailable" when the fetch fails (404 for trashed or deleted documents). Saved views open via `WorkspaceViewModel.openSavedView(_:)`. The discussion is a sheet on `DocumentDetailView` (`showingDiscussion`).
- **Server URL**: the app knows its server as the URL in `SessionRestoration.signedIn(url)`, normalised on entry by `ServerAddress.parse` (lowercase scheme, path prefix kept, trailing slash, query and fragment dropped). Host case and default ports are not normalised.
- **Web routes**: `vault::scoped_router` rewrites `/vaults/{id}/<tail>` onto the scoped HTML routes, so `/vaults/{vault_id}/documents/{id}`, `/vaults/{vault_id}/` (with `?view=all`) and `/vaults/{vault_id}/saved-views/{id}` already exist. Unauthenticated GETs redirect to `/login?next=…`. There is no separate discussion page; notes and comments render inside the document detail.
- **Project**: entitlements and Info.plist are generated by XcodeGen from `apple/Folio/project.yml`. There is no associated-domains entitlement and no `NSUserActivityTypes`. Bundle IDs, team, app group, keychain group and Release `match AppStore …` profiles are literals in target settings. The app group is also a literal in `ServerConfig.appGroup`, and the OAuth callback scheme is a literal in `OAuthConfiguration`.
- **Server**: `/.well-known/` is in `EXEMPT_PREFIX` (no auth). Only OAuth metadata is served there. Settings precedence follows the `mcp_default` + `settings_repo` pattern.

## Goals / Non-Goals

**Goals:**

- Put all decision logic (payload codec, canonical server comparison, URL building and parsing, routing decision, held continuation) in FolioKit as pure, `swift test`-able code. The app target only wires SwiftUI modifiers to it.
- One resolver for Handoff, universal links and (for lock handling) Spotlight.
- Keep the official App Store build's resolved bundle IDs, entitlements and signing identical, while letting other teams build Folio with their own identifiers.

**Non-Goals:**

- Browser→app for the App Store build. Associated domains are compiled into the signed entitlements, and every self-hosted server has its own domain. A wildcard (`applinks:*.example.com`) only covers subdomains of one domain the publisher controls, so it does not help.
- `webcredentials` (password AutoFill) in the association file. It would be a cheap follow-up on the same route but is unrelated to Handoff.
- Handing over unsaved state: drafts of notes or comments, scroll position, an in-progress upload or scan, search text.
- Account switching or multi-server support in the app.
- Changing Spotlight identifiers (the `apple-server-contract` requirement stays as is).

## Decisions

### 1. Which screens advertise

| Screen                                                         | Advertises                              | Reason                                                                                                                                                                                                                                     |
| -------------------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Document detail                                                | yes (`com.cedricziel.folio.document`)   | The main reason to use Handoff: open the same document on the bigger screen.                                                                                                                                                               |
| Document discussion sheet                                      | yes, same type with `pane=discussion`   | The discussion is part of a document, not a separate place. A separate type would add a declaration and a fallback URL for no gain. The web fallback is the document page, which already includes notes and comments.                      |
| Vault library: Inbox / All documents                           | yes (`com.cedricziel.folio.library`)    | Cheap, and it carries the vault choice, which is the one thing users reselect by hand.                                                                                                                                                     |
| Saved view                                                     | yes (`com.cedricziel.folio.saved-view`) | Saved views are stored on the server, so their IDs are valid on every device of the same user. The web page exists.                                                                                                                        |
| Search                                                         | **no**                                  | The query is user-typed text that could be sensitive. It would end up in the activity, which conflicts with the privacy goal. Results are transient. While searching, the underlying library activity keeps advertising, without the text. |
| Upload / scan review                                           | **no**                                  | Refers to local files that do not exist on the other device.                                                                                                                                                                               |
| Classifications, settings, App lock settings, sources activity | **no**                                  | Administrative. Nothing worth continuing, and App lock settings are device-local.                                                                                                                                                          |

Activity types are fixed reverse-DNS strings, not derived from the bundle ID. Handoff pairs apps only within one Team ID, so a self-build under another team never collides with the official app, and fixed strings keep FolioKit free of bundle lookups.

### 2. Payload: flat `userInfo`, versioned, built on #392

PR #392 (transferable documents) adds `DocumentActivityPayload` (`com.cedricziel.folio.document`, keys `version` = Int 1, `server`, `vault`, `document`, validated on decode) and `DocumentActivityTracker`, which already writes the document activity in `DocumentDetailView` with Handoff turned off. Handoff extends that payload instead of defining a parallel one: `HandoffPayload { server: URL, vault: UUID, target: .document(UUID, pane: .discussion?) | .library(.inbox | .all) | .savedView(UUID) }`, where the `.document` case encodes to exactly #392's keys plus an optional `pane`, so both decoders accept each other's documents. Library and saved-view activities use the same `version`/`server`/`vault` keys plus `list` or `savedView`. `requiredUserInfoKeys` = `["version", "server", "vault"]` plus the target key. The sender writes its signed-in URL. Canonicalisation happens on comparison (Decision 3), so #392's `server.absoluteString` is compatible as-is. This is chosen over a `Codable` blob in a single `Data` key because it is inspectable in tests, works with `requiredUserInfoKeys`, and an unknown future key is simply ignored. A different `version` fails decoding, and the app falls back to `webpageURL` (spec: "Malformed or newer payload"). `title` stays as #392 sets it (the document title, for the system's on-screen awareness). It travels only between the user's own devices and is never read for routing; user info and keywords carry no names. A closed draft of continuation logic (`DocumentHandoff`, PR #394 on `claude/feat-175-handoff`) covers version and server validation, cold-launch restore and sign-out withdrawal with tests. The implementer may port it into `HandoffResolver` / `ContinuationInbox` where it matches this design.

### 3. Server identity = canonical base URL

`ServerIdentity(url)` canonicalises:
- lowercase the scheme
- lowercase the host and convert an internationalised host to its IDNA/punycode form, so `bücher.example`, its percent-encoded spelling and `xn--bcher-kva.example` are equal
- keep IPv6 literals bracketed (`[::1]`)
- drop the default port
- drop user info, query and fragment
- trim trailing `/` from the path, keeping its case

The receiver compares the canonical forms of the payload's `server` and of its own session URL. Because the comparison canonicalises both sides, #392's raw `server.absoluteString` stays compatible.

Alternative considered: compare the OAuth `issuer` from `/.well-known/oauth-authorization-server`, which equals the server's `public_url`. It would match a phone using `https://folio.lan` with a Mac using `https://folio.example.com` for the same server. Rejected for now: the app does not persist the issuer, and resolving it on the receiver needs a network round trip before routing. A URL mismatch fails safe: the user gets the browser fallback, not wrong data.

### 4. Routing decision is a pure function over every session state

`HandoffResolver.decide(incoming: Incoming, session: SessionRestoration) -> HandoffDecision`, where `Incoming` is `.activity(type, userInfo, webpageURL)`, `.universalLink(URL)` or `.spotlight(DocumentLink)`. "Same" means the canonical server matches the session's URL. Spotlight carries no server and counts as the session's server.

| `SessionRestoration` | Handoff / universal link | Spotlight |
|---|---|---|
| `.restoring` | `.hold` | `.hold` |
| `.signedOut` | `.signIn(prefill: server, then: route)` | `.ignore` |
| `.signedIn(url)`, same | `.open(route)` | `.open(route)` |
| `.signedIn(url)`, other | `.otherServer(host, web)` | n/a |
| `.expired(url)` / `.interrupted(url)`, same | `.hold` | `.hold` |
| `.expired(url)` / `.interrupted(url)`, other | `.otherServer(host, web)` | n/a |
| `.unavailable(server: url?, _)`, same, or `nil` | `.hold` | `.hold` |
| `.unavailable(server: url, _)`, other | `.otherServer(host, web)` | n/a |

An unparseable universal link, or a malformed payload that has a `webpageURL`, gives `.openInBrowser(URL)` in every state. Anything else gives `.ignore`. `.hold` keeps the item in the inbox, and it is decided again on every session change. Only `AppModel.signOut()` (`inbox.clear()`) discards it. Any other transition to `.signedOut` (for example, restoration finding no credentials after `FolioSessionChanged`) re-decides the held item, which becomes `.signIn(prefill:)`. This matches the spec's "Continuation waits for the same server's session" and "Continuation never changes the account" requirements.

`HandoffRoute` maps 1:1 onto existing workspace calls. Vault and document availability are not checked by the resolver. They need the network, and `WorkspaceViewModel.open` and the document destination already produce the spec'd "vault no longer available" and "Document unavailable" states. Two additions are needed: `open` takes a `pane` so the discussion sheet is presented, and a saved-view route reports a missing saved view.

`HandoffPresentation.from(_ decision:, currentServer:)` is a second pure function. It maps a decision to what the UI shows: `.navigate(route)`, `.alert(title, message, browserURL)`, `.browser(URL)`, `.prefillSignIn(URL)` or `.nothing`. The alert text ("This document is on {host}. You're signed in to {current host}.") is therefore unit-tested, and the SwiftUI code only switches over it.

Universal-link parsing (`HandoffLink.parse(URL)`) finds the last `/vaults/{uuid}` segment pair; everything before it is the server path prefix. It then matches `""`, `documents/{uuid}` or `saved-views/{uuid}` exactly, and reads `?view=all`. `HandoffLink.webURL(for: HandoffPayload)` builds the reverse, so the two are tested as a round trip.

### 5. One continuation inbox per app, handled in one existing window

`AppModel` owns a single `ContinuationInbox` (FolioKit, `@MainActor @Observable`), so there is one per app process, not one per window. The inbox holds at most one pending item (last one wins), tagged with the scene that received it. A scene's identity is a per-window `@State private var sceneID = UUID()` in `RootView`, passed to `receive(_:scene:)` and `take(scene:…)`. `.onDisappear` calls `inbox.sceneClosed(sceneID)`. `RootView` installs `.onContinueUserActivity` for the three Folio types, `NSUserActivityTypeBrowsingWeb` and `CSSearchableItemActionType`; each calls `inbox.receive(_:scene:)`. The `WindowGroup` content gets `.handlesExternalEvents(preferring: ["*"], allowing: ["*"])`. With that, the system delivers each continuation to the frontmost existing window instead of opening a new one, on macOS and on iPad with several scenes. `RootView` stays mounted in every state (locked, signed out, signed in), unlike `InboxView`. The Spotlight handler moves out of `InboxView`.

`take(scene:isLocked:session:)` returns `nil` while locked or while the decision is `.hold`. Otherwise it returns the item only to the scene that received it; once `sceneClosed` has been called for that `sceneID`, any scene may take it. It removes the item on return, so each continuation is handled exactly once. The workspace in the receiving window takes it when `workspace.isReady` (the vault catalog has loaded), when `lock.isLocked` changes to false, and when the session changes. `OnboardingView` takes `.signIn` decisions to prefill the address. `AppModel.connected(to:)` re-decides, and the route is dropped if the server differs. `signOut()` calls `inbox.clear()`.

Alternative considered: keep handlers in `InboxView` and add a lock check. Rejected because `InboxView` does not exist while locked or signed out, which is exactly when the item must be held.

### 6. Advertising: one `.userActivity` per window, chosen by a pure function

`HandoffAdvertiser.payload(for: AdvertisingState) -> HandoffPayload?` (FolioKit) decides what a window advertises. Its input is the session URL, `isLocked`, the selected vault, the destination (inbox, all or saved-view ID), the selected document ID and `showingDiscussion`. The rules:
- `nil` when locked or not signed in
- a `.document` payload, with `pane = .discussion` exactly when `showingDiscussion` is true, when a document is selected
- otherwise a `.library` or `.savedView` payload

Search text is not an input, so it cannot leak.

Wiring:
- `DocumentDetailView` keeps a **single** `.userActivity` (the one from #392's `.documentActivity` modifier, or one new modifier if Handoff lands first). Its `isActive` is `payload != nil`, and its update closure calls `HandoffActivity.configure(activity, payload:)`. `showingDiscussion` feeds the pane. The discussion sheet adds no modifier of its own.
- `InboxView` has one `.userActivity` for library and saved-view types, with `isActive` = `session.selection == nil && payload != nil`. In a split view with a selected document, only the detail's activity is active.
- `HandoffActivity.configure` sets `userInfo`, `requiredUserInfoKeys`, `webpageURL` and `isEligibleForHandoff = true`. It sets `isEligibleForSearch`, `isEligibleForPublicIndexing` and `isEligibleForPrediction` to false. For documents it extends #392's `DocumentActivityTracker.configure`, keeping its title and `targetContentIdentifier`.

Views are torn down on lock, sign-out and vault switch (`WorkspaceView` is keyed by `.id(url)` and the inbox by `.id(workspace.session.id)`), so SwiftUI invalidates the activity. `isLocked` in the advertiser covers the privacy-cover window that is still mounted.

**Shared with #353.** PR #392 already publishes the document activity on `DocumentDetailView` with `isEligibleForHandoff = false`. Handoff flips that and adds the payload extras, rather than adding a second modifier. Handoff donates nothing to Spotlight, so the per-server Spotlight scoping in #380 is unaffected.

### 7. Other-server and browser fallback UI

The app renders `HandoffPresentation` (Decision 4): an alert with **Open in Browser** and **Cancel**, or a browser view. **Open in Browser** and `.browser` use `SFSafariViewController` on iOS and `NSWorkspace.shared.open` on macOS. On iOS, `SFSafariViewController` never hands a URL back to an app through universal links, so a self-built app cannot bounce a link back to itself in a loop.

### 8. Server: `apple.app_ids` and the association route

- **folio-core**: `models::AppleAppId(String)` with `FromStr` validation `^[A-Z0-9]{10}\.[A-Za-z0-9][A-Za-z0-9.-]*$`, plus `parse_list(&str)`, which splits on commas and newlines and trims. It is a pure value type, so no new port is needed. The existing `SettingsRepository` stores the DB value under `apple.app_ids` as newline-separated text.
- **folio-infra**: `Config.apple: AppleConfig { app_ids: Vec<String> }` with `#[serde(default)]` (a TOML array in `config.toml`). The env var `FOLIO_APPLE__APP_IDS` is registered in the existing env-setting table with `ValueKind::List`. That kind already turns a comma-separated string into a list for `import_roots` and forward-auth (`crates/folio-infra/src/config.rs`, the `ValueKind::List` arm of the env parser). No custom deserialiser is needed. `Config::validate` rejects invalid entries and names `apple.app_ids`.
- **folio-api**: `AppState.apple_app_ids_default: Vec<AppleAppId>` (like `mcp_default`). A new `routes/apple.rs` serves `GET /.well-known/apple-app-site-association`. It reads `settings_repo.get("apple.app_ids")` per request (one indexed key lookup; Apple's CDN fetches rarely) and falls back to the default when the row is empty or missing. It returns 404 when the result is empty; otherwise `Json` with `Cache-Control: public, max-age=3600`. The router merges at the root next to the auth router. The path is already auth-exempt. It is not vault-scoped and not under `/api`, so it is **not** added to `openapi/openapi.json`, and the generated Swift client is unchanged.
- **Body**: exact `?` masks for UUIDs, so the patterns need no `*`, no exclusions, and no reasoning about how `*` behaves around `/`. With `U = ????????-????-????-????-????????????` and `{p}` the path of `server.public_url` (empty at the domain root):

```json
{
  "applinks": {
    "details": [
      {
        "appIDs": ["ABCDE12345.com.example.folio"],
        "components": [
          { "/": "{p}/vaults/U/documents/U" },
          { "/": "{p}/vaults/U/saved-views/U" },
          { "/": "{p}/vaults/U/" }
        ]
      }
    ]
  }
}
```

  Sub-resources (`/download`, `/entries`, `/search`, `/saved-views/new`, …) never match because their shape differs. The `?view=all` query is not part of the path match, so it rides along on the vault-root pattern. Apple only fetches the file from the domain root. A Folio served under a path prefix needs the reverse proxy to forward `/.well-known/apple-app-site-association` to Folio, and the README documents that rule. A snapshot test pins the JSON.
- **Freshness**: the server returns the new body on the next request. Devices, however, read the association through Apple's CDN, which refreshes on its own schedule, so a change can take a while to reach devices, and the server cannot force it. Developer-mode associated domains (`?mode=developer`) bypass the CDN for development-signed builds. The `/settings` help text and `docs/deployment.md` both say this.
- **Precedence limitation**: an empty DB value falls back to `config.toml`/env, following the AI-key convention. An app ID set in config therefore cannot be turned off from `/settings`. `/settings` shows the source, and `docs/configuration.md` states the limitation.
- **Settings UI**: a new "Apple app links" section in the `/settings` template. It has a textarea with one app ID per line, posted to `POST /settings/apple` (an HTML form behind `require_admin`, which redirects with `Redirect::to("/settings?saved=apple")`). It shows the effective source ("from settings", "from config.toml", "not configured"), the association URL to check, and the CDN note. Any new colors or spacing come from the shared design-system tokens the settings sections already use.

### 9. Self-builds: identifiers come from one xcconfig

XcodeGen target `settings` override xcconfig values. Today the following are literals in `project.yml`, so a `Local.xcconfig` that only sets `PRODUCT_BUNDLE_IDENTIFIER` or `CODE_SIGN_ENTITLEMENTS` would be ignored:
- `PRODUCT_BUNDLE_IDENTIFIER` for the app and both extensions
- `DEVELOPMENT_TEAM`
- `CODE_SIGN_ENTITLEMENTS`, which XcodeGen derives from `entitlements.path`
- Release manual signing and `match` profile names
- the app group, also hardcoded in `ServerConfig.appGroup`
- the keychain group
- the OAuth callback scheme in `OAuthConfiguration`

Other teams can build Folio only if these come from variables:

- **`apple/Folio/Config/Folio.xcconfig`** (checked in; project-level `configFiles` for Debug and Release) defines the official values and ends with `#include? "Local.xcconfig"`. The variables are:
  - `FOLIO_DEVELOPMENT_TEAM = WPW3QSLZ2F`
  - `FOLIO_BUNDLE_ID = com.cedricziel.folio`
  - `FOLIO_APP_GROUP = group.com.cedricziel.folio`
  - `FOLIO_ASSOCIATED_DOMAINS =` (empty)
  - `FOLIO_APP_ENTITLEMENTS = Resources/Folio.entitlements`
  - `FOLIO_RELEASE_SIGN_STYLE = Manual`
  - the six profile names: `FOLIO_PROFILE_APP_IOS = match AppStore $(FOLIO_BUNDLE_ID)`, `FOLIO_PROFILE_APP_MACOS = match AppStore $(FOLIO_BUNDLE_ID) macos`, and the same pairs for `.share` and `.fileprovider`
  - `FOLIO_RELEASE_IDENTITY = Apple Distribution`
- **`project.yml`** references only variables:
  - `DEVELOPMENT_TEAM: $(FOLIO_DEVELOPMENT_TEAM)`
  - `PRODUCT_BUNDLE_IDENTIFIER: $(FOLIO_BUNDLE_ID)`, `$(FOLIO_BUNDLE_ID).share` and `$(FOLIO_BUNDLE_ID).fileprovider`
  - `CODE_SIGN_ENTITLEMENTS: $(FOLIO_APP_ENTITLEMENTS)` set explicitly in the app target's settings, so it wins over the path XcodeGen derives
  - Release `CODE_SIGN_STYLE: $(FOLIO_RELEASE_SIGN_STYLE)`, `PROVISIONING_PROFILE_SPECIFIER[sdk=…]: $(FOLIO_PROFILE_…)` and `CODE_SIGN_IDENTITY[sdk=…]: $(FOLIO_RELEASE_IDENTITY)`
  - entitlements `com.apple.security.application-groups: [$(FOLIO_APP_GROUP)]` and `keychain-access-groups: [$(AppIdentifierPrefix)$(FOLIO_BUNDLE_ID)]`
  - Info.plist `FolioKeychainGroup: $(AppIdentifierPrefix)$(FOLIO_BUNDLE_ID)`, new `FolioAppGroup: $(FOLIO_APP_GROUP)` and `FolioCallbackScheme: $(FOLIO_BUNDLE_ID)` in all three targets, and `NSExtensionFileProviderDocumentGroup: $(FOLIO_APP_GROUP)`

  The build-time expansion of `$(VAR)` in entitlements and Info.plist is the same mechanism that already resolves `$(AppIdentifierPrefix)`.
- **FolioKit** reads the app group and callback scheme from Info.plist, the way `SharedConfiguration` already reads `FolioKeychainGroup`. `UserDefaultsServerConfigStore.appGroup` and `OAuthConfiguration.callbackScheme` / `redirectURI` become lookups of `FolioAppGroup` / `FolioCallbackScheme`, falling back to today's literals when the key is absent (unit tests, SwiftPM). The OAuth redirect URI becomes `<scheme>:/oauth/callback`. The server registers clients dynamically, so it needs no change.
- **`Config/Local.xcconfig.example`** documents the overrides a self-builder sets:
  - `FOLIO_DEVELOPMENT_TEAM`, `FOLIO_BUNDLE_ID`, `FOLIO_APP_GROUP`
  - `FOLIO_RELEASE_SIGN_STYLE = Automatic`, `FOLIO_RELEASE_IDENTITY = Apple Development`, and the six `FOLIO_PROFILE_*` set empty
  - `FOLIO_ASSOCIATED_DOMAINS = folio.example.com`
  - `FOLIO_APP_ENTITLEMENTS = Resources/Folio-Local.entitlements`

  `Config/Local.xcconfig` and `Resources/Folio-Local.entitlements` are git-ignored.
- **Associated domains**: `apple/scripts/associated-domains.sh` copies the generated `Folio.entitlements` to `Folio-Local.entitlements` and adds `com.apple.developer.associated-domains = [applinks:<each host>]` with PlistBuddy. With `FOLIO_ASSOCIATED_DOMAINS` empty it does nothing. The official entitlements never contain the key: the App Store profile has no Associated Domains capability, and an empty key would break signing.
- **Fastlane**: `generate_project` is a private helper in `apple/fastlane/Fastfile`. The official lanes and `lane :test` (and therefore CI) all call it. It runs the script only `if File.exist?("#{APPLE_DIR}/Folio/Config/Local.xcconfig")`, so CI never depends on a local file. Self-builders can run `xcodegen generate && apple/scripts/associated-domains.sh` directly.
- **Verification**: a script compares `xcodebuild -showBuildSettings` for the Folio, FolioShare and FolioFileProvider targets in two cases:
  - without `Local.xcconfig`: the resolved values equal today's literals (`com.cedricziel.folio*`, team `WPW3QSLZ2F`, the match profiles, `Resources/Folio.entitlements`)
  - with `Config/Local.xcconfig.example` copied in: the overridden values, with Release resolving to Automatic signing, `Apple Development` and empty profile specifiers

  CI runs the first case.
- Private/LAN servers cannot be fetched by Apple's CDN. The README documents `applinks:host?mode=developer` for development-signed builds with Associated Domains Development enabled on the device.
- `NSUserActivityTypes` is in the Info.plist of every build, because app→app Handoff needs no entitlement.

### 10. Tests and CI

- **FolioKit** (`apple/FolioKit/Tests/FolioKitTests`, run by `xcrun swift test` inside `fastlane test`; `.github/workflows/apple.yml` runs that on `macos-26` for `apple/**` changes):
  - `HandoffPayloadTests`: round trip; compatibility with #392's `DocumentActivityPayload`; required keys; bad UUID; wrong version; no name leakage.
  - `ServerIdentityTests`: a table of equal and unequal pairs, including `https://bücher.example` = `https://xn--bcher-kva.example`, `http://[::1]:8080/` = `http://[::1]:8080`, and `http://[::1]:8080` ≠ `http://[::1]`.
  - `HandoffLinkTests`: web URLs with and without a path prefix; parsing; round trip; rejected sub-resources.
  - `HandoffResolverTests`: every row of the Decision 4 table.
  - `HandoffPresentationTests`: decision → presentation, including the alert text.
  - `HandoffAdvertiserTests`: the selected document wins over the library; `pane` follows `showingDiscussion`; nothing while locked or signed out; library or saved view when nothing is selected; search text never appears.
  - `ContinuationInboxTests`: held while locked; last one wins; delivered once; scene targeting with fallback when the receiving scene closes; cleared on sign-out.
  - `AppConfigurationTests`: Info.plist lookup of the app group and callback scheme, with fallback.
- **App target**: `FolioAuthTests` already compiles `AppLock.swift`. It gains `AppLockContinuationTests`, which drives `AppLock` + `ContinuationInbox` through lock → receive → failed unlock → unlock and asserts delivery exactly once. `NavigationTests` is an XCUITest fixture and cannot read `NSUserActivity`, so it is not used for advertising checks. CI also asserts:
  - the official generated `Folio.entitlements` has no `com.apple.developer.associated-domains` key
  - the official `-showBuildSettings` values are unchanged
- **Server** (`crates/folio-api/tests/apple_links.rs`, run by `make test` in the Rust CI):
  - 404 when unset, also with auth enabled and no session
  - 200 JSON with headers and the exact masked components, with and without a path prefix
  - DB overrides config, and an empty DB value falls back
  - `/apple-app-site-association` is not served
  - `POST /settings/apple` returns 303, 422 and 403 in the spec'd cases

  folio-core unit tests cover `AppleAppId`; folio-infra config tests cover the TOML array, the env list and an invalid value. The existing `web.rs` tests gain coverage for the stable URLs.
- Handoff between real devices cannot run in CI. The PR checklist includes one manual iPhone→Mac pass and one two-window Mac pass.

## Risks / Trade-offs

- [The same server reached through two URLs (LAN vs public) is treated as two servers] → The user gets the browser fallback, which is safe. Issuer-based identity is a possible follow-up (Decision 3).
- [Apple's CDN serves a stale association after a change] → This is documented in `/settings` and the deployment docs. `?mode=developer` helps during development. The resolver still gates every link, so an outdated match opens in the in-app browser.
- [Self-hosters on private networks cannot use Universal Links in release builds] → This is documented as a limitation; Handoff and the web fallback still work.
- [Turning identifiers into variables could change the official build by accident] → The `-showBuildSettings` and entitlements checks in CI compare against today's literals.
- [A held continuation could reveal something after unlock that the user no longer wants] → Only the last item is held. It is cleared on sign-out, and it only navigates; nothing is shown before authentication.
- [`webpageURL` with `http://` LAN servers] → `NSUserActivity` allows it. The receiving browser may warn, and that is the operator's choice.
- [Self-builders misconfigure the Team ID or bundle ID] → `/settings` shows the effective app IDs and the association URL. The README checklist matches `FOLIO_DEVELOPMENT_TEAM.FOLIO_BUNDLE_ID` against the server setting.

## Migration Plan

No data migration. The new settings key is absent by default, so existing servers answer 404 on the association path, as they effectively do today. Rollback: remove `apple.app_ids` (config and settings row), and the route returns 404 again. The app changes ship in the next App Store release. Older app versions ignore the new activity types.
