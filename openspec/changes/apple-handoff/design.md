# Design

## Context

See proposal.md (Why) for motivation. Current state, as found in the code:

- **Continuation today**: only `InboxView` handles a continuation (`.onContinueUserActivity(CSSearchableItemActionType)`). It parses `DocumentLink(spotlightIdentifier:)` (vault + document UUID, no server) and calls `handle(.document(id, vaultID:))` → `WorkspaceViewModel.open(_:vaultID:)`. `RootView` renders `AppLockView` _instead of_ `WorkspaceView` while `AppLock.isLocked`, so no continuation handler exists while locked: a Spotlight tap into a locked app is dropped today.
- **Navigation**: `WorkspaceViewModel.open` already selects the vault, reports `"This vault is no longer available."` for unknown vaults, and pushes the document onto the All-documents path. `InboxView.documentDestination` already shows "Document unavailable" when the fetch fails (404 for trashed or deleted documents). Saved views open via `WorkspaceViewModel.openSavedView(_:)`. The discussion is a sheet on `DocumentDetailView` (`showingDiscussion`).
- **Server URL**: the app knows its server as the URL in `SessionRestoration.signedIn(url)`, normalised on entry by `ServerAddress.parse` (lowercase scheme, path prefix kept, trailing slash, query and fragment dropped). Host case and default ports are not normalised.
- **Web routes**: `vault::scoped_router` rewrites `/vaults/{id}/<tail>` onto the scoped HTML routes, so `/vaults/{vault_id}/documents/{id}`, `/vaults/{vault_id}/` (with `?view=all`) and `/vaults/{vault_id}/saved-views/{id}` already exist. Unauthenticated GETs redirect to `/login?next=…`. There is no separate discussion page; notes and comments render inside the document detail.
- **Project**: entitlements and Info.plist are generated by XcodeGen from `apple/Folio/project.yml`. There is no associated-domains entitlement and no `NSUserActivityTypes`. Release signing uses `match AppStore com.cedricziel.folio` profiles.
- **Server**: `/.well-known/` is in `EXEMPT_PREFIX` (no auth). Only OAuth metadata is served there. Settings precedence follows the `mcp_default` + `settings_repo` pattern.

## Goals / Non-Goals

**Goals:**

- Put all decision logic (payload codec, canonical server comparison, URL building and parsing, routing decision, held continuation) in FolioKit as pure, `swift test`-able code. The app target only wires SwiftUI modifiers to it.
- One resolver for Handoff, universal links and (for lock handling) Spotlight.
- Leave the official App Store build's entitlements and signing untouched.

**Non-Goals:**

- Browser→app for the App Store build. Associated domains are compiled into the signed entitlements, and every self-hosted server has its own domain. A wildcard (`applinks:*.example.com`) only covers subdomains of one domain the publisher controls, so it does not help.
- `webcredentials` (password AutoFill) in the association file. It would be a cheap follow-up on the same route but is unrelated to Handoff.
- Handing over unsaved state: drafts of notes or comments, scroll position, an in-progress upload or scan, search text.
- Account switching or multi-server support in the app.
- Changing Spotlight identifiers (the `apple-server-contract` requirement stays as is).

## Decisions

### 1. Which screens advertise

| Screen                                                         | Advertises                              | Reason                                                                                                                                                                                                                                     |
| -------------------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Document detail                                                | yes (`com.cedricziel.folio.document`)   | The main reason to use Handoff: open the same document on the bigger screen.                                                                                                                                                               |
| Document discussion sheet                                      | yes, same type with `pane=discussion`   | The discussion is part of a document, not a separate place. A separate type would add a declaration and a fallback URL for no gain. The web fallback is the document page, which already includes notes and comments.                      |
| Vault library: Inbox / All documents                           | yes (`com.cedricziel.folio.library`)    | Cheap, and it carries the vault choice, which is the one thing users reselect by hand.                                                                                                                                                     |
| Saved view                                                     | yes (`com.cedricziel.folio.saved-view`) | Saved views are stored on the server, so their IDs are valid on every device of the same user. The web page exists.                                                                                                                        |
| Search                                                         | **no**                                  | The query is user-typed text that could be sensitive. It would end up in the activity, which conflicts with the privacy goal. Results are transient. While searching, the underlying library activity keeps advertising, without the text. |
| Upload / scan review                                           | **no**                                  | Refers to local files that do not exist on the other device.                                                                                                                                                                               |
| Classifications, settings, App lock settings, sources activity | **no**                                  | Administrative. Nothing worth continuing, and App lock settings are device-local.                                                                                                                                                          |

Activity types are fixed reverse-DNS strings, not derived from the bundle ID. Handoff pairs apps only within one Team ID, so a self-build under another team never collides with the official app, and fixed strings keep FolioKit free of bundle lookups.

### 2. Payload: flat string `userInfo`, versioned

`HandoffPayload { server: URL, vault: UUID, target: .document(UUID, pane: .discussion?) | .library(.inbox | .all) | .savedView(UUID) }` encodes to `[String: String]`: `v`="1", `server`, `vault`, `document`/`pane`/`list`/`savedView`. `requiredUserInfoKeys` = `["v", "server", "vault"]` plus the target key. This is chosen over a `Codable` blob in a single `Data` key because it is inspectable in tests, works with `requiredUserInfoKeys`, and an unknown future key is simply ignored. A different `v` fails decoding, and the app falls back to `webpageURL` (spec: "Malformed or newer payload"). `title` is set to the generic "Folio", never the document title.

### 3. Server identity = canonical base URL

`ServerIdentity(url)` canonicalises: lowercase scheme and host, drop the default port, drop user info, query and fragment, trim trailing `/` from the path, keep the path case. The sender writes its canonical signed-in URL. The receiver compares it with the canonical form of its own signed-in URL.

Alternative considered: compare the OAuth `issuer` from `/.well-known/oauth-authorization-server`, which equals the server's `public_url`. It would match a phone using `https://folio.lan` with a Mac using `https://folio.example.com` for the same server. Rejected for now: the app does not persist the issuer, and resolving it on the receiver needs a network round trip before routing. A URL mismatch fails safe: the user gets the browser fallback, not wrong data. This can be added later as a second identity key without changing the spec's outcomes.

### 4. Routing decision is a pure function

`HandoffResolver.decide(incoming: Incoming, session: SessionRestoration) -> HandoffDecision`, where `Incoming` is `.activity(type, userInfo, webpageURL)`, `.universalLink(URL)` or `.spotlight(DocumentLink)`. Results:

- `.open(HandoffRoute)` when signed in to the same server (Spotlight always counts as the current server).
- `.signIn(prefill: URL, then: HandoffRoute)` when `.signedOut` / `.expired` / `.interrupted`.
- `.otherServer(host: String, web: URL)` when signed in elsewhere.
- `.openInBrowser(URL)` for an unparseable universal link or a malformed payload that has a `webpageURL`.
- `.ignore` otherwise.

`.restoring` is not decided yet: the inbox keeps the incoming item and decides again when restoration finishes.

`HandoffRoute` maps 1:1 onto existing workspace calls. Vault and document availability are not checked by the resolver. They need the network, and `WorkspaceViewModel.open` and the document destination already produce the spec'd "vault no longer available" and "Document unavailable" states. Two additions are needed: `open` must accept a `pane` so the discussion sheet is presented, and a saved-view route must report a missing saved view.

Universal-link parsing (`HandoffLink.parse(URL)`) finds the last `/vaults/{uuid}` segment pair. Everything before it is the server path prefix. It then matches `""`, `documents/{uuid}` or `saved-views/{uuid}` exactly, and reads `?view=all`. `HandoffLink.webURL(for: HandoffPayload)` builds the reverse, so the two are tested as a round trip.

### 5. One continuation inbox at the root, gated by App lock

A new `@MainActor @Observable ContinuationInbox` in FolioKit holds at most one pending `Incoming` (last one wins). `RootView` installs `.onContinueUserActivity` for the three Folio types, `NSUserActivityTypeBrowsingWeb` and `CSSearchableItemActionType`. They all call `inbox.receive(_:)`. `RootView` stays mounted in every state (locked, signed out, signed in), unlike `InboxView`. The Spotlight handler moves out of `InboxView`.

The inbox releases the item only through `take(isLocked:session:)`, which returns `nil` while locked or restoring. `WorkspaceView` consumes it when `workspace.isReady` (the vault catalog has loaded) and on `lock.isLocked` changing to false. `OnboardingView` consumes `.signIn` decisions to prefill the address and keeps the route until sign-in. `AppModel.connected(to:)` re-runs the decision and drops the route if the server differs. `signOut()` calls `inbox.clear()`.

Alternative considered: keep handlers in `InboxView` and add a lock check. Rejected because `InboxView` does not exist while locked or signed out, which is exactly when the item must be held.

### 6. Advertising with SwiftUI `.userActivity`

`DocumentDetailView`, the discussion sheet, and `InboxView` (library or saved view) use `.userActivity(type, isActive:) { activity in HandoffActivity.configure(activity, payload:) }`. `HandoffActivity.configure` (FolioKit) sets `userInfo`, `requiredUserInfoKeys`, `webpageURL`, `title`, `isEligibleForHandoff = true`, and `isEligibleForSearch`, `isEligibleForPublicIndexing` and `isEligibleForPrediction = false`. `needsSave` follows SwiftUI's lifecycle. Because the views are removed when locked, signed out or switching vault (`WorkspaceView` is keyed by `.id(url)` and the inbox by `.id(workspace.session.id)`), SwiftUI invalidates the activity, which is what the "Activities follow the session" spec asks for. `isActive` is additionally bound to `!lock.isLocked` so that a privacy-covered but not yet locked window still advertises (no content leaks), while a locked one does not.

**One activity per view, shared with #353.** Transferable documents (#353, branch `claude/feat-353-transferable-documents`) also associates an `NSUserActivity` / App Entity with `DocumentDetailView` to identify the on-screen document to the system. A view should publish a single current activity. If #353 lands first, Handoff extends that activity with `HandoffActivity.configure` (adding the payload, `webpageURL` and eligibility flags) rather than adding a second `.userActivity` modifier. If Handoff lands first, #353 builds on this one. Both are compatible with the privacy flags here: an App Entity association needs no search or public-indexing eligibility. Handoff donates nothing to Spotlight, so the per-server Spotlight scoping in #380 is unaffected.

### 7. Other-server and browser fallback UI

`.otherServer` shows an alert: "This document is on {host}. You're signed in to {current host}." with **Open in Browser** and **Cancel**. **Open in Browser** and `.openInBrowser` use `SFSafariViewController` on iOS and `NSWorkspace.shared.open` on macOS. On iOS, `SFSafariViewController` never hands a URL back to an app through universal links, so a self-built app cannot bounce a link back to itself in a loop.

### 8. Server: `apple.app_ids` and the association route

- **folio-core**: `models::AppleAppId(String)` with `FromStr` validation `^[A-Z0-9]{10}\.[A-Za-z0-9][A-Za-z0-9.-]*$` and a `parse_list(&str)` that splits on commas and newlines and trims. It is a pure value type, so no new port. The existing `SettingsRepository` stores the DB value under `apple.app_ids` as newline-separated text.
- **folio-infra**: `Config.apple: AppleConfig { app_ids: Vec<String> }` with `#[serde(default)]`. Figment's env provider maps `FOLIO_APPLE__APP_IDS`, and a custom deserialiser accepts either a TOML array or a comma-separated string. `Config::validate` rejects invalid entries, naming `apple.app_ids`. It is listed in the configuration lookup table next to `server.public_url`.
- **folio-api**: `AppState.apple_app_ids_default: Vec<AppleAppId>` (like `mcp_default`). A new `routes/apple.rs` serves `GET /.well-known/apple-app-site-association`. It reads `settings_repo.get("apple.app_ids")` per request (one indexed key lookup; Apple's CDN fetches rarely), falls back to the default, and returns 404 when empty. Otherwise it returns `Json` with `Cache-Control: public, max-age=3600`. The router merges at the root next to the auth router. The path is already auth-exempt. It is not vault-scoped and not under `/api`, so it is **not** added to `openapi/openapi.json`, and the generated Swift client is unchanged.
- **Body** (component order matters: Apple evaluates in order, and `*` can match across `/`, so exclusions come first):

```json
{
  "applinks": {
    "details": [
      {
        "appIDs": ["ABCDE12345.com.example.folio"],
        "components": [
          { "/": "/vaults/*/documents/search", "exclude": true },
          { "/": "/vaults/*/documents/upload", "exclude": true },
          { "/": "/vaults/*/documents/*/*", "exclude": true },
          { "/": "/vaults/*/saved-views/new", "exclude": true },
          { "/": "/vaults/*/saved-views/*/*", "exclude": true },
          { "/": "/vaults/*/documents/*" },
          { "/": "/vaults/*/saved-views/*" },
          { "/": "/vaults/*/" }
        ]
      }
    ]
  }
}
```

The vault root is claimed only in its trailing-slash form (`/vaults/*/`), which is the form the app writes into `webpageURL`. Because `*` can cross `/`, a bare `/vaults/*` pattern would also claim every vault sub-page not excluded above (`/vaults/{id}/trash`, `/vaults/{id}/manage`, …). Any matched path the app does not route still opens in the in-app browser (spec: "Link to an unsupported page"). A snapshot test pins the final JSON shape. Apple only fetches the file from the domain root. A Folio served under a path prefix (`server.public_url = https://example.com/folio`) therefore needs the reverse proxy to forward `/.well-known/apple-app-site-association` to Folio. The handler prepends the `public_url` path to every pattern, and the README documents the proxy rule.

- **Settings UI**: a new "Apple app links" section in the `/settings` template, a textarea with one app ID per line, posted to `POST /settings/apple` (an HTML form behind `require_admin`, returning `Redirect::to("/settings?saved=apple")`). It shows the effective source ("from settings", "from config.toml", "not configured") and the association URL to check. Any new colors or spacing come from the shared design-system tokens already used by the settings sections.

### 9. App-side associated domains for self-builders

The official build must keep exactly today's entitlements, because the App Store provisioning profile has no Associated Domains capability, and adding the key, even empty, breaks signing.

- `project.yml` gives the Folio target `configFiles: { Debug: Config/Folio.xcconfig, Release: Config/Folio.xcconfig }`. `Config/Folio.xcconfig` contains only `FOLIO_ASSOCIATED_DOMAINS =` and `#include? "Local.xcconfig"`.
- A self-builder copies `Config/Local.xcconfig.example` to the git-ignored `Config/Local.xcconfig`. In it they set `FOLIO_ASSOCIATED_DOMAINS = folio.example.com`, `DEVELOPMENT_TEAM`, `PRODUCT_BUNDLE_IDENTIFIER`, and `CODE_SIGN_ENTITLEMENTS = Folio/Resources/Folio-Local.entitlements`.
- `apple/scripts/associated-domains.sh` (run after `xcodegen generate`, and by a `fastlane generate_project` step when `Local.xcconfig` exists) copies the generated `Folio.entitlements` to the git-ignored `Folio-Local.entitlements` and adds `com.apple.developer.associated-domains = [applinks:<each host>]` with PlistBuddy. With `FOLIO_ASSOCIATED_DOMAINS` empty it does nothing.
- Private/LAN servers cannot be fetched by Apple's CDN. The README documents `applinks:host?mode=developer` for development-signed builds with Associated Domains Development enabled on the device.
- `NSUserActivityTypes` is added to the generated Info.plist in every build, because app→app Handoff needs no entitlement.

### 10. Tests and CI

- **FolioKit** (`apple/FolioKit/Tests/FolioKitTests`, run by `xcrun swift test` inside `fastlane test`, which `.github/workflows/apple.yml` runs on `macos-26` for `apple/**` changes):
  - `HandoffPayloadTests`: round trip; required keys; bad UUID; wrong version; no title or name leakage.
  - `ServerIdentityTests`: a table of equal and unequal URL pairs.
  - `HandoffLinkTests`: web URL building with and without a path prefix; universal-link parsing, including rejected download and entries paths; round trip.
  - `HandoffResolverTests`: every decision for every session state.
  - `ContinuationInboxTests`: held while locked, last wins, cleared on sign-out, released on unlock, held while restoring.
- **App target**: `FolioAuthTests` already compiles `AppLock.swift`. An `AppLockContinuationTests` there drives `AppLock` + `ContinuationInbox` through lock → receive → failed unlock → unlock, and asserts delivery exactly once. A CI step asserts that the generated official `Folio.entitlements` has no `com.apple.developer.associated-domains` key.
- **Server** (`crates/folio-api/tests/apple_links.rs`, run by `make test` in the Rust CI): 404 when unset; 200 JSON, headers and exact components when configured via config; DB overrides config; empty DB falls back; no auth needed with auth enabled; `/apple-app-site-association` not served; `POST /settings/apple` 303, 422 and 403. Also: folio-core unit tests for `AppleAppId` and folio-infra config tests for TOML array, env string and invalid value. The existing `web.rs` tests gain coverage for the stable URLs (200, trashed 404, login redirect `next`).
- Handoff between real devices cannot run in CI. The PR checklist includes one manual iPhone→Mac pass.

## Risks / Trade-offs

- [Same server reached through two URLs (LAN vs public) is treated as different] → The user gets the browser fallback, which is safe. Issuer-based identity is a documented follow-up (Decision 3).
- [AASA `*` semantics differ from intuition and Apple caches the file through its CDN for a long time] → Exclusions come first. A snapshot test pins the JSON. The app's resolver is the real gate, and unsupported matches open in an in-app browser. The docs explain how to force a refresh (`?mode=developer`, reinstall).
- [Self-hosters on private networks cannot use Universal Links in release builds] → This is documented as a limitation, and Handoff and the web fallback still work.
- [A held continuation could reveal something after unlock that the user no longer wants] → Only the last item is held, it is cleared on sign-out, and it only navigates. It never shows content before authentication.
- [`webpageURL` with `http://` LAN servers] → Allowed by `NSUserActivity`. The receiving browser may warn, and that is the operator's choice.
- [Self-builders misconfigure Team ID or bundle ID] → `/settings` shows the effective app IDs and the association URL. The README has a checklist that matches `DEVELOPMENT_TEAM.PRODUCT_BUNDLE_IDENTIFIER` against the server setting.

## Migration Plan

No data migration. The new settings key is absent by default, so existing servers answer 404 on the association path, as they effectively do today. Rollback: remove `apple.app_ids` (config and settings row), and the route returns 404 again. The app changes ship in the next App Store release. Older app versions ignore the new activity types.
